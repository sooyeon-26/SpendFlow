SpendFlow 프로젝트 소개
소비를 기록하는 가계부에서, 소비 흐름을 알려주는 서비스로

한 줄 소개
SpendFlow는 번거로운 소비 기록과 뒤늦은 예산 확인 문제를 해결하기 위해, 소비 입력부터 분석, 위험 감지, 외부 알림까지 하나의 흐름으로 연결한 iPhone 최적화 PWA입니다.


1. 문제 정의

기존 가계부는 사용자가 소비할 때마다 금액과 카테고리를 직접 입력해야 하고, 예산 상태를 확인하기 위해 다시 앱을 열어 숫자와 차트를 해석해야 합니다.

이 과정에서 두 가지 문제가 발생한다고 판단했습니다.

- 반복 입력으로 인한 기록 피로가 크다.
- 예산 초과나 과소비 위험을 뒤늦게 발견한다.

따라서 SpendFlow의 목표를 단순히 소비 내역을 저장하는 것이 아니라, 사용자가 적게 입력하고도 현재 소비 상태를 즉시 이해하며 위험할 때 먼저 안내받는 경험으로 정의했습니다.


2. 해결 과정

첫째, 소비 입력 과정의 마찰을 줄였습니다.

금액을 가장 먼저 입력하고 카테고리와 결제수단을 버튼으로 선택하도록 구성했습니다. 메모는 선택 사항으로 두었습니다. “스타벅스 6800원 카드”와 같은 문장 입력 기능은 메인 기능이 아니라 빠른 입력 폼을 자동으로 채워주는 보조 기능으로 배치했습니다.

둘째, 예산 숫자를 직관적인 감각으로 번역했습니다.

월 예산 사용률을 물의 수위로 표현해 사용자가 복잡한 숫자를 읽지 않아도 현재 상태를 바로 인지할 수 있도록 했습니다. 첫 화면에서는 예산 수위에 집중하고, 오늘 소비, 주간 흐름, 카테고리 분석과 같은 상세 정보는 아래 영역으로 분리했습니다.

셋째, 앱 안의 확인을 앱 밖의 행동으로 연결했습니다.

소비가 저장되면 월 예산 사용률과 하루 소비 금액을 자동으로 계산합니다. 예산 80% 도달, 예산 100% 초과, 하루 소비 50,000원 이상과 같은 조건을 감지해 webhook payload를 생성하고, n8n과 Slack 알림으로 확장할 수 있도록 설계했습니다.


3. 기술 구조

기술 스택

- React
- TypeScript
- Vite
- Tailwind CSS
- Zustand
- localStorage
- PWA
- n8n Webhook / Slack 연동 구조

데이터 흐름

React UI
  ↓ 사용자 입력
Zustand Store
  ↓ 데이터 CRUD
expenseRepository
  ↓
localStorage

소비 저장 이벤트
  ↓
분석 및 위험 조건 감지
  ↓
Webhook payload 생성
  ↓
n8n
  ↓
Slack 소비 요약 및 위험 알림

MVP에서는 백엔드 없이 빠르게 기능을 검증하기 위해 localStorage를 사용했습니다. 다만 컴포넌트가 localStorage를 직접 사용하지 않도록 expenseRepository 계층을 분리했습니다.

따라서 향후 Supabase, Firebase 또는 별도 API를 도입할 때 화면과 상태 관리 구조는 유지하고 Repository 내부 구현만 교체할 수 있습니다.


4. 핵심 기능

1) 빠른 소비 기록

금액 우선 입력, 카테고리 버튼, 결제수단 버튼, 선택 메모와 저장으로 이어지는 짧은 입력 동선을 구현했습니다.

2) 문장 기반 자동 채우기

소비 문장에서 금액, 가맹점, 카테고리와 결제수단을 추출해 빠른 입력 폼에 자동으로 반영합니다.

3) 인터랙티브 예산 수위

Canvas 기반 파동 시뮬레이션으로 월 예산 사용률을 물의 높이로 표현했습니다. 물 영역에서는 터치로 파동을 만들 수 있으며, 페이지 스크롤 영역과 제스처가 충돌하지 않도록 분리했습니다.

4) 소비 분석 리포트

오늘, 주간, 월간 소비 합계와 최근 7일 소비 흐름을 계산합니다. 또한 상위 소비 카테고리, 반복 소비, 카테고리별 예산 위험 상태와 다음 행동을 제공합니다.

5) 선제적 위험 감지

월 예산 80% 도달, 100% 초과, 하루 소비 50,000원 이상 조건을 감지해 경고 수준, 메시지와 행동 제안을 생성합니다.

6) PWA 모바일 경험

iPhone safe area, standalone 모드, 홈 화면 아이콘과 세로 화면 중심의 앱 셸을 구현해 모바일 웹을 실제 앱처럼 사용할 수 있도록 했습니다.


5. 성과

- 소비 입력부터 저장, 대시보드 반영, 분석, 위험 감지, webhook payload 생성까지 전체 사용자 흐름을 구현했습니다.
- Repository 계층을 통해 빠른 MVP 개발과 향후 백엔드 교체 가능성을 함께 확보했습니다.
- 393 × 852 iPhone 화면을 기준으로 터치, 스크롤, safe area와 하단 내비게이션을 검증했습니다.
- 물 영역의 터치 제스처와 페이지 스크롤 영역을 분리해 모바일 인터랙션 충돌을 해결했습니다.
- 최종 디자인 QA에서 P0, P1, P2 수준의 문제 없이 검증을 완료했습니다.
- TypeScript 및 Vite 프로덕션 빌드를 통과했습니다.

현재 단계의 성과는 사용자 수나 전환율과 같은 상용 서비스 지표가 아니라, 핵심 제품 가설을 실제로 동작하는 MVP와 확장 가능한 기술 구조로 구현한 것입니다.


6. 회고

잘한 점

물 수위라는 시각적 은유를 단순한 장식으로 사용하지 않고, 예산 사용률, 위험 구간과 터치 인터랙션까지 일관되게 연결했습니다. 또한 localStorage를 선택하면서도 Repository 계층을 분리해 프로토타입의 빠른 개발이 장기적인 기술 부채로 바로 이어지지 않도록 했습니다.

아쉬운 점

현재 문장 자동 분류는 실제 AI 모델이 아니라 키워드 기반 mock 로직입니다. 소비 데이터도 단일 기기의 localStorage에 저장되기 때문에 로그인, 여러 기기 동기화와 데이터 복구를 지원하지 않습니다. n8n 정기 알림 역시 실제 서비스에서는 브라우저가 아니라 백엔드 API를 기준으로 실행해야 합니다.

다음 단계

- 실제 사용자를 대상으로 소비 입력 완료 시간과 중도 이탈률을 측정합니다.
- 자동 분류 결과의 수정률을 수집해 분류 정확도를 개선합니다.
- 위험 알림 확인률과 이후 소비 변화를 측정해 알림 임계값을 조정합니다.
- 사용자 인증과 서버 데이터베이스를 도입해 여러 기기 동기화를 지원합니다.
- 실제 AI 분류 API를 연결하고 실패 시 기존 parser를 fallback으로 사용합니다.


면접용 마무리

SpendFlow를 통해 단순히 화면을 구현하는 데서 끝나지 않고, 사용자의 입력 행동을 줄이는 제품 설계, 소비 데이터를 의미 있는 피드백으로 바꾸는 분석 로직, 그리고 외부 자동화까지 연결되는 전체 흐름을 설계하고 구현했습니다.

특히 빠르게 검증해야 하는 MVP의 제약 안에서도 저장소와 자동화 계층을 분리해, 현재의 개발 속도와 향후 서비스 확장성을 함께 고려했습니다.


작성 근거 및 한계
